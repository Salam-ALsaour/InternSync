## 1. Purpose

Increments 1 to 4 built and tested every function of the SRS (F1–F19). This last increment adds no function. It prepares what is handed over at the end of the project:

- a final report;
- the requirements status;
- a user guide;
- the script of the final demonstration;
- the final presentation;
- the documents as files for submission.

User acceptance testing (M6) stays prepared but is not run now: on Oct 29 the project owner decided to finish the other work first (Section 6).

## 4. Decisions

| **ID** | **Open point** | **Decision (recommended and adopted)** |
|:---|:---|:---|
| RQ-1 | Language of the deliverables | English, like every project document; the system and the screenshots can be shown in Arabic during the demonstration |
| RQ-2 | Where the presentation is made | A slide deck made with Claude's slide tool, from the Key Results numbers, downloadable as PowerPoint and PDF. Its link goes into the README and the final report |
| RQ-3 | How the PDFs are produced | A small Node script renders each Markdown document to HTML and prints it with the Chromium of the browser tests (no new program to install). The SRS keeps its own build on the course template (Word) |
| RQ-4 | Requirements status | Generated by `docs/tools/trace.py`: requirement IDs and priorities from the SRS, the delivering increment from each increment's requirements, the tests from the test code and the test reports |
| RQ-5 | Screenshots of the user guide | Taken by a Playwright script from the demo data, in English, at desktop size and phone size, so they can be taken again after any change |
| RQ-6 | User acceptance testing | Not run now (owner's decision, Oct 29). The plan stays ready; O8 and the device check are reported as open in the final report, the SPMP, and Key Results. The risk "volunteers not available in time" has occurred |
| RQ-7 | Reference deployment | Stays prepared and off until the owner creates the accounts (Deployment, Section 3); the final demonstration runs on the local Docker stack, as the SPMP allows |

## 5. Checks (testing phase)

| **Check** | **Expected result** |
|:---|:---|
| C-1 Links | Every relative link and image in the maintained documents points to a file that exists |
| C-2 Traceability | Every requirement ID of the SRS appears once in the requirements status; every Must and Should requirement has a test or a recorded browser check |
| C-3 Screenshots | The script takes every screenshot of the user guide without error on the demo data |
| C-4 Exports | One PDF per maintained document, opening with its diagrams and tables; the SRS Word and PDF built on the template |
| C-5 Demo dry run | The demo script runs from fresh demo data without help, within 15 minutes |
| C-6 Review | Each deliverable read against this document; numbers in the final report and the deck equal Key Results |
| C-7 Regression | CI green: backend, frontend, browser tests |

## 6. Risks

| **Risk** | **Effect** | **Response** |
|:---|:---|:---|
| UAT not run before the final delivery | O8 (80% of scenarios without help) not measured | Reported as open everywhere; the plan, cards, and sheet are ready to run at any time, even after M7 |
| Numbers differ between the report, the deck, and Key Results | Contradictions in front of the examiners | Key Results is the single source; C-6 compares them |
| Screenshots or PDFs out of date after a change | Wrong documents handed in | Both are produced by scripts and rebuilt at the end of the increment |
